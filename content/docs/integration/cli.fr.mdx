Les workflows en ligne de commande utilisent deux outils indépendants :

- [`tidas`](https://github.com/tiangong-lca/tidas-tools/releases/tag/v0.1.3) est l'exécutable Rust
  natif publié pour la conversion locale TIDAS/eILCD, l'import de données ACV externes, la
  validation de packages, l'export de base de données et le packaging déterministe de versions.
- `tiangong-lca` est le client de plateforme TianGong LCA distribué via npm pour les requêtes
  distantes, l'écriture de brouillons, la revue et d'autres workflows d'API.

Ces commandes ne sont pas des alias. Appelez `tidas` directement pour le travail local sur les
packages ; ne supposez pas que `tiangong-lca` l'appelle en interne.

## Installer `tidas` 0.1.3

Les archives précompilées sont le canal privilégié pour l'utilisateur final et ne requièrent aucun
runtime Rust, Python, Java ou Node.js. Les installateurs téléchargent une archive immuable et son
fichier `.sha256`, puis les vérifient avant l'installation.

### Linux et macOS

```bash
curl --proto '=https' --tlsv1.2 -fsSLO \
  https://github.com/tiangong-lca/tidas-tools/releases/download/v0.1.3/install.sh
sh install.sh --version 0.1.3 --prefix "$HOME/.local"
"$HOME/.local/bin/tidas" --version
```

Ajoutez `$HOME/.local/bin` au `PATH` si votre shell ne l'inclut pas déjà.

### Windows PowerShell

```powershell
Invoke-WebRequest `
  https://github.com/tiangong-lca/tidas-tools/releases/download/v0.1.3/install.ps1 `
  -OutFile install.ps1
.\install.ps1 -Version 0.1.3
& "$env:LOCALAPPDATA\Programs\tidas\bin\tidas.exe" --version
```

Si l'invite le demande, ajoutez ce répertoire `bin` au `PATH`.

### Plateformes précompilées

| Plateforme | Archive de version |
| --- | --- |
| Linux x86_64 | `tidas-v0.1.3-x86_64-unknown-linux-gnu.tar.gz` |
| Linux ARM64 | `tidas-v0.1.3-aarch64-unknown-linux-gnu.tar.gz` |
| macOS Intel | `tidas-v0.1.3-x86_64-apple-darwin.tar.gz` |
| macOS Apple Silicon | `tidas-v0.1.3-aarch64-apple-darwin.tar.gz` |
| Windows x86_64 | `tidas-v0.1.3-x86_64-pc-windows-msvc.zip` |

Chaque archive de la [version v0.1.3](https://github.com/tiangong-lca/tidas-tools/releases/tag/v0.1.3)
est accompagnée d'un SHA-256 et d'un SBOM SPDX. Windows ARM64 est hors de la matrice de support
actuelle. La version contient aussi des formules Homebrew et des manifestes Winget ; leur présence
ne signifie pas qu'ils ont été soumis à un tap externe ou au dépôt communautaire Winget.

### Installation depuis crates.io

Les développeurs disposant de Rust 1.88+ et des dépendances de développement libxml2/libxslt
peuvent installer depuis les sources :

```bash
cargo install tidas --version 0.1.3 --locked
tidas --version
tidas version --format json
```

Le paquet crates.io et l'exécutable installé se nomment tous deux `tidas`.

## Workflows de packages `tidas`

### Importer un format externe vers TIDAS

`tidas import` prend en charge EcoSpold 1/2, SimaPro CSV, openLCA JSON-LD, XLSX de processus
openLCA et les entrées ILCD/eILCD. Le format est normalement détecté :

```bash
tidas import ./openlca-package.zip \
  --output ./imported \
  --target tidas \
  --format json

tidas validate ./imported/tidas \
  --input-format tidas-json \
  --issues ./imported/validation-issues.jsonl \
  --format json
```

Les sorties par défaut incluent `import-report.json`, `issues.jsonl`, `tidas/` et
`process-bundles/<process_uuid>/`. Ajoutez `--write-mapping` pour générer `mapping.csv.gz` en vue
d'une revue par champ, ou `--no-process-bundles` si les packages de dépendances par processus sont
inutiles. `.zolca` n'est pas pris en charge ; exportez d'abord un format d'échange supporté depuis
openLCA.

### Convertir entre TIDAS et eILCD

```bash
tidas convert ./tidas-package \
  --output ./eilcd-package \
  --to ilcd \
  --format json

tidas convert ./eilcd-data \
  --output ./tidas-package \
  --to tidas \
  --format json
```

Les données converties se trouvent dans le sous-répertoire `data/` du répertoire de sortie.
Validez la représentation cible avant téléversement ou usage en aval :

```bash
tidas validate ./eilcd-package/data --input-format ilcd-xml --format json
tidas validate ./tidas-package/data --input-format tidas-json --format json
```

### Rapports et codes de sortie

Avec `--format json`, la sortie standard ne contient que le rapport lisible par machine. Persistez
les problèmes complets avec des options propres à chaque commande telles que `--issues` ; utilisez
l'option globale `--report <PATH>` pour écrire le rapport d'opération de façon atomique.

| Code | Signification |
| ---: | --- |
| `0` | succès |
| `2` | commande terminée avec des problèmes de données |
| `64` | erreur d'utilisation ou d'option |
| `69` | capacité connue actuellement indisponible |
| `70` | erreur interne |
| `74` | échec d'E/S requis |
| `130` | opération annulée |

Les pipelines doivent inspecter à la fois le code de sortie et les champs JSON tels que `status`,
`exit_class`, `diagnostics`, `artifacts` et `summary` ; ne parsez pas le seul texte du terminal.

## Installer et exécuter `tiangong-lca`

Pour les requêtes distantes, l'écriture de brouillons et les workflows de revue, exécutez une fois
le dernier paquet publié :

```bash
npm exec --yes --package=@tiangong-lca/cli@latest -- tiangong-lca --help
npm exec --yes --package=@tiangong-lca/cli@latest -- tiangong-lca doctor
```

Installation globale :

```bash
npm install --global @tiangong-lca/cli
tiangong-lca --help
tiangong-lca doctor
```

## Variables d'environnement

Les commandes distantes utilisent l'autorisation navigateur Supabase OAuth 2.1. Configurez l'URL de l'API, la clé publiable et l'identifiant public du client OAuth propre à l'environnement :

```bash
TIANGONG_LCA_API_BASE_URL=
TIANGONG_LCA_SUPABASE_PUBLISHABLE_KEY=
TIANGONG_LCA_OAUTH_CLIENT_ID=
TIANGONG_LCA_AUTH_MODE=oauth
TIANGONG_LCA_REGION=us-east-1
```

- `TIANGONG_LCA_API_BASE_URL` peut pointer vers la racine du projet, `/functions/v1` ou `/rest/v1`.
- `TIANGONG_LCA_OAUTH_CLIENT_ID` est un identifiant public, pas un secret ; Dev et Production utilisent des ID différents.
- Exécutez d'abord `tiangong-lca auth status --json`. Si le résultat est `login-required`, l'utilisateur exécute lui-même `tiangong-lca auth login` dans un terminal de confiance, puis se connecte et consent dans le navigateur.
- Le CLI conserve les jetons d'accès et de rafraîchissement rotatifs dans un fichier de session local privé et les actualise au besoin. Les sorties n'affichent ni jeton, ni adresse e-mail complète, ni chemin de session.
- Utilisez `tiangong-lca auth whoami --json` pour une identité live expurgée et `tiangong-lca auth doctor-auth --json` avant une écriture sensible au compte.
- `auth logout` supprime uniquement la session locale. Pour empêcher immédiatement les prochains rafraîchissements, révoquez TianGong CLI dans les applications connectées du compte ; un jeton d'accès court déjà émis peut rester valide jusqu'à son expiration.

Ne donnez jamais à une IA, à un argument de commande ou à un chat un nom d'utilisateur, mot de passe, code d'autorisation ou jeton d'accès/rafraîchissement. Une automatisation headless approuvée ne peut recevoir qu'un `TIANGONG_LCA_ACCESS_TOKEN` court injecté par son orchestrateur ; Supabase OAuth ne propose ni grant password ni client-credentials. Utilisez un `TIANGONG_LCA_SESSION_FILE` privé distinct pour chaque contexte compte/projet/client.

## Commandes de release de données LCI/LCIA

`tiangong-lca release ...` est la famille de commandes distantes du plan de contrôle des releases de
données LCI/LCIA. Ce n'est ni le workflow de publication du paquet npm, ni un alias du constructeur
local de packages `tidas`. Elle utilise la session OAuth décrite ci-dessus ; le serveur vérifie
toujours l'accès `data_product_manager` pour les lectures privées et les opérations mutatives, et
n'accepte pas de service-role key.

La séquence habituelle est :

```bash
tiangong-lca release prepare --input ./release-prepare.json --json
tiangong-lca release upload --input ./release-upload.json --output ./upload-receipt.json
tiangong-lca release finalize --input ./release-finalize.json --json
tiangong-lca release approve --input ./release-approval.json --json
tiangong-lca release publish --input ./release-publish.json --json
tiangong-lca release readback-verify --input ./release-readback.json --json
tiangong-lca release status --release-run-id <release-run-id> --json
```

Les artefacts de release restent centrés fichier : la requête d'upload doit déclarer pour chaque ZIP
son profil, son format, son chemin, sa taille en octets et son SHA-256. Le CLI vérifie les octets
locaux avant de demander les URL d'upload signées. Les reçus, téléchargements et projections de
Calculation Bundle sont écrits dans des fichiers privés plutôt que d'envoyer de gros payloads vers
stdout.

```bash
tiangong-lca release calculation-bundle --package-id <package-id> --output ./calculation-bundle.json
tiangong-lca release calculation-artifact --package-id <package-id> --artifact-path chunks/lci-00000.jsonl.gz --output ./lci-00000.jsonl.gz
tiangong-lca release current --json
tiangong-lca release artifact-download --artifact-id <artifact-id> --output ./release.zip
```

`calculation-bundle` ne renvoie qu'une projection de manifeste vérifiée avec des URL de téléchargement
courtes. Avant de télécharger un artefact, vérifiez que le chemin exact figure dans ce manifeste ;
après le téléchargement, le CLI revérifie la taille et le SHA-256. Ajoutez `--dry-run` pour inspecter
une forme de requête avec identifiants masqués, et ne transmettez pas d'identifiants ni d'URL signées
à une IA ou à un chat.

Utilisez l'aide intégrée pour toutes les options :

```bash
tiangong-lca flow --help
tiangong-lca process --help
tiangong-lca lifecyclemodel --help
tiangong-lca review --help
tiangong-lca release --help
```

## Portes d'automatisation

Pour les pipelines de production de données, le CLI fournit aussi des commandes de contrôle qualité
utiles avant l'écriture, la publication ou la remise à un relecteur :

```bash
tiangong-lca process identity-preflight --input ./process-preflight.json --out-dir ./process-preflight --json
tiangong-lca flow identity-preflight --input ./flow-preflight.json --out-dir ./flow-preflight --json
tiangong-lca process build-plan validate --input ./process-build-plan.json --out-dir ./process-build-plan --json
tiangong-lca flow build-plan validate --input ./flow-build-plan.json --out-dir ./flow-build-plan --json
tiangong-lca publish run --input ./publish-request.json --dry-run --json
```

- `identity-preflight` compare un processus ou un flux cible aux données candidates et indique si l'automatisation peut le réutiliser, doit le router vers une revue manuelle, ou doit bloquer une nouvelle création.
- `build-plan validate` vérifie qu'un plan de construction de processus ou de flux inclut les décisions d'identité, les liaisons de preuve, les plans de nommage, les décisions `unit_of_analysis` et les champs obligatoires de flux de référence ou de propriété de flux.
- `dataset evidence-search plan/run` planifie la récupération de preuves publiques au niveau des champs et enregistre les résultats de recherche externes ; le CLI possède la matrice de requêtes, le budget, la normalisation des résultats et les artefacts de déclaration de preuve, tandis que les workflows humains ou d'agents conservent le jugement sur les sources.
- `publish run --dry-run` rapporte les résultats du règleset de publication avant une véritable écriture ou publication.

Ces commandes écrivent des rapports lisibles par machine sous `outputs/` ou `reports/` dans le
`--out-dir` choisi. Pour l'automatisation, lisez des champs tels que `status`, `blockers`,
`issues`, `files` et les chemins d'artefacts plutôt que de vous fier au texte du terminal.

## Maintenance des jeux de données

`tiangong-lca dataset maintenance plan/apply/verify` sert au nettoyage contrôlé au niveau du compte,
à la réparation de mauvais imports, à la fusion d'alias de données de support et aux reconstructions
protégées de dérivés de processus. Il s'exécute comme l'utilisateur actuellement authentifié et
s'appuie sur la RLS côté serveur pour limiter les lignes visibles et modifiables ; ne le traitez pas
comme un outil batch d'administration entre comptes.

```bash
tiangong-lca dataset maintenance plan --scope ./maintenance-scope.json --operation redo-import --out-dir ./dataset-maintenance --page-size 1000 --timeout-ms 10000 --json
tiangong-lca dataset maintenance plan --scope ./derivative-rebuild-scope.json --operation rebuild-derivatives --out-dir ./derivative-rebuild --json
tiangong-lca dataset maintenance apply --plan ./dataset-maintenance/maintenance-plan.json --commit --approve-plan <sha256> --confirm <current-account-email> --timeout-ms 10000 --json
tiangong-lca dataset maintenance verify --plan ./dataset-maintenance/maintenance-plan.json --out-dir ./dataset-maintenance/verify --page-size 1000 --timeout-ms 10000 --json
tiangong-lca dataset maintenance plan --scope ./alias-scope.json --operation merge-support-aliases --out-dir ./dataset-maintenance --json
tiangong-lca dataset maintenance flow-identity --help
```

Utilisez `merge-support-aliases` uniquement pour réparer des alias de données de support protégés
en owner-draft. Le `apply` ordinaire n'est pas le repli d'une exécution de production scellée :
construisez d'abord le plan immuable, utilisez `freeze-protected` pour relire le périmètre de
production exact et générer la demande d'approbation, utilisez `seal-protected-approval` pour
enregistrer localement l'approbation humaine octet pour octet, puis utilisez `run-protected`
uniquement pour exécuter ou inspecter une exécution de production scellée. `verify` doit juger le
résultat à partir d'une preuve de relecture fraîche plutôt qu'en faisant confiance au seul rapport
apply/run. Le préflight reste lié à l'expiration côté serveur ; le CLI ne tolère qu'un faible décalage
d'horloge serveur en avance et ne prolonge pas la validité de l'approbation ou de l'exécution. La
vérification des dérivés relie l'action evidence du domaine base de données au snapshot frais ; ne
comparez pas directement le JSON canonique du CLI avec `jsonb::text` PostgreSQL comme s'ils relevaient
du même domaine de hash.

La maintenance d'identité de flux Step 3 utilise le sous-workflow dédié
`dataset maintenance flow-identity` et ne réutilise jamais le runner Step 2. L'ordre habituel est :
`capture` pour un recensement production en lecture seule et une attestation base de données, `plan`
à partir de la politique de compatibilité, du ledger de revue et du live capture, `freeze` puis
`seal-approval` pour lier les octets exacts d'exécution, `run` pour soumettre en série le prochain
durable ordinal et finaliser seulement lorsque les dérivés sont prêts, puis `verify` pour relire
indépendamment le périmètre terminal, les lignes sources, les lignes publiques/support, les processus
affectés et la fermeture de références owner-draft. Si une réponse est ambiguë, si le wrapper se
termine sans son permit en mémoire, ou si les dérivés deviennent prêts plus tard, continuez seulement
avec `freeze-recovery`, `seal-recovery-approval` et `run-recovery` ; ne rejouez pas automatiquement
les écritures de processus dans la même invocation.

`--page-size` est le maximum demandé, de `1-5000` ; PostgREST peut tout de même renvoyer des pages
plus petites à cause d'une limite côté serveur. Le CLI demande `Prefer: count=exact`, valide le total
exact et la plage retournée depuis chaque `Content-Range`, puis avance l'offset suivant du nombre de
lignes réellement renvoyées. Un scan accepté doit conserver un ordre strict `id` / `version`, sans
identités manquantes ni dupliquées, et enregistre pour chaque table la taille de page demandée, la
taille effective, le nombre de pages, les lignes lues, le total exact et les compteurs agrégés
d'entités.

Cette preuve de complétude signifie que le CLI a parcouru le résultat filtré pendant que les membres
de la table et les clés de tri restaient stables. Comme la lecture couvre plusieurs requêtes HTTP,
ce n'est pas un snapshot transactionnel ou MVCC d'un instant unique ; évitez tout nettoyage,
suppression ou insertion concurrent pour le même compte pendant la maintenance. `plan` lie la preuve
de complétude au hash immuable du plan, `apply` relance le scan complet du compte et les contrôles de
dérive avant d'accepter l'approbation ou d'écrire, et `verify` utilise une preuve fraîche de relecture
complète au lieu de faire confiance au seul rapport apply.

`rebuild-derivatives` ne peut cibler qu'un seul processus brouillon de l'utilisateur courant, à une
version exacte. Le scope doit déclarer `action: "rebuild_derivatives"`, `target_mode: "owner_draft"`,
le propriétaire courant attendu, le `state_code: 0` attendu, ainsi que l'ensemble complet de
composants `extracted_md` et `embedding_ft`. L'opération reconstruit uniquement le Markdown et les
embeddings dérivés ; elle ne modifie pas la charge utile principale du processus, son propriétaire,
son état ni `modified_at`, et ne peut pas cibler de ligne publique/partagée, de propriétaire tiers,
de ligne non brouillon, d'autre table, plusieurs lignes ou un sous-ensemble de composants.

Pour `rebuild-derivatives`, un `apply` réussi signifie seulement que la RPC de base de données
protégée a accepté et mis la demande en file. Cela ne signifie pas que la génération Markdown ou
embedding est terminée. Le CLI ne propose aucun repli vers un appel Edge direct,
`admin embedding-run`, une file brute, SQL, des identifiants service-role ou une mutation REST brute ; la
réexécution du même plan doit retourner la même preuve de demande durable. `verify` lit la demande
durable et un nouveau snapshot des dérivés du processus, puis ne rapporte que `pending`, `passed` ou
`failed`. Il ne passe que lorsque les deux dérivés demandés sont à jour et que les préconditions
gelées des champs primaires correspondent toujours ; traitez `pending` et `failed` comme des états
non réussis.

## Validation et rapports d'échec `tiangong-lca`

`dataset validate`, `process save-draft`, `lifecyclemodel save-draft` et les commandes de réparation
apparentées exécutent une validation locale du schéma TIDAS avant l'écriture. En cas d'échec de la
validation rapide, le CLI actuel utilise une validation approfondie adossée au SDK pour fournir des
chemins et messages de problème plus précis.

Cela signifie :

- les données qui passent la validation continuent d'utiliser le chemin rapide ;
- les données invalides doivent renvoyer des chemins de champs, codes et messages plus actionnables ;
- avant toute écriture `--commit`, les lignes invalides au regard du schéma sont bloquées et consignées dans `failures.jsonl` ou le rapport de validation du répertoire de sortie.
- Les chemins de schéma TIDAS `common:classification` / `common:category` peuvent s'arrêter à leur profondeur de catégorie naturelle ; n'ajoutez pas de classes inférieures vides juste pour remplir la hiérarchie. Les chemins trop profonds, niveaux dupliqués ou valeurs invalides restent bloqués.
- Pour les écritures de brouillons par lots, passez `--target-user-id` avec `process save-draft --commit`. Le CLI vérifie la session d'authentification courante et tout propriétaire de brouillon visible avant l'écriture, tandis que la vérification par relecture prouve toujours le propriétaire final et la charge utile.
- `dataset save-draft` continue par défaut d'empêcher l'écriture en brouillons locaux au compte des Unit Groups, Flow Properties et autres configurations de base purement référentielles. Utilisez `--allow-account-local-support`, ou définissez `TIANGONG_ALLOW_ACCOUNT_LOCAL_SUPPORT=1`, uniquement pour des migrations ou réparations contrôlées ayant délibérément besoin de ces lignes de support dans Mes données ; les opérateurs interactifs devraient préférer les lignes existantes de la base.
- `dataset classification apply --type location` peut créer l'objet parent et le champ cible manquants lorsque `target_path` pointe explicitement vers un champ de localisation dérivé du schéma. Les chemins ambigus ou champs hors localisation restent bloqués.
- `dataset evidence-search run` écrit le plan de recherche, les résultats normalisés, le rapport et, lorsque les preuves sont insuffisantes ou partielles, une déclaration de preuve JSON sous `outputs/`.

Pour les intégrations de pipeline `tiangong-lca`, lisez les champs JSON tels que `status`,
`counts`, `issues`, `files` et les artefacts `outputs/**` générés plutôt que de vous fier au seul
texte du terminal. Pour l'import local de packages, la conversion ou la validation complète d'un
package, utilisez la commande `tidas` indépendante décrite ci-dessus.
